# VectoRune 设计符合性审查

审查日期：2026-11-09

设计依据：根目录 `README.md` 中补充的项目介绍

代码基线：`25bcc09`，结合审查时的本地目录状态

## 结论

项目的功能方向基本符合 README，但核心架构尚未达到“轻量、高性能、面向低资源 ARM、地图格式插件化”的目标。目前更准确的定位是：已经打通主要功能的桌面原型。

现有代码可以作为后续工程化的基础，尤其是本地 MBTiles 直读、MapLibre 渲染、旧解析库的进程隔离、独立 GPX 解析和回归测试。后续重点应转向核心接口、数据访问方式、持久化索引和目标设备验收。

本次审查没有修改实现代码。后续改造见 [实施记录](refactoring-progress-2026-11-09.md)。
本文保留当时结论，不代表改造后的当前状态。文件链接随目录迁移更新；
原始实现可通过 `git show 25bcc09:mapviewer/mapdocument.cpp` 等命令查看。

## 审查范围与限制

重点检查了：

- `mapviewer/` 的界面、地图加载、搜索、定位和导航实现。
- `mapviewer/garmin/` 与 `lib/libgarmin/` 的解析接入和路由数据流。
- 根目录与 mapviewer 的构建、安装配置。
- `tools/`、`scripts/`、`web/`、`navit/`、`navitdrv/` 的职责和接入状态。
- 当前北京佳明地图的导入与单次寻路开销。

这不是对全部第三方源码的逐行安全审计，也没有在目标 ARM 开发板上验证性能、功耗和部署。性能测量是当前 Mac 本地构建的单次结果，不能代替 Release 构建或目标设备基准测试。

## 主要发现

优先级说明：P1 表示会阻碍核心架构或目标平台落地；P2 表示能力完整性、扩展性或工程质量方面的差距。

### 1. [P1] 地图格式还没有真正插件化

当前 `MapDocument` 根据文件扩展名分支处理地图：MBTiles 走 MapLibre，IMG 调用佳明转换程序。搜索、POI 查询和路线规划也直接放在同一个类里。新增格式需要修改主程序，没有统一的格式接口、能力声明和注册机制。

当前使用的 MapLibre Qt Location 插件属于渲染后端插件，并不等于 README 中设想的地图格式插件。

证据：

- [地图加载分支](../core/mapdocument.cpp)
- [搜索实现](../core/mapdocument.cpp)
- [佳明库直接编译链接](../plugins/garmin/CMakeLists.txt)

建议：先建立格式适配接口与能力声明，将瓦片、几何、搜索和路由能力分开表达。第一阶段采用编译期注册即可，不必立即实现动态加载。

### 2. [P1] 佳明数据处理方式与低资源目标冲突明显

加载 IMG 时，程序一次性提取最高精度的全部几何，转换为完整 GeoJSON，同时生成 POI 和路网 JSON。该方案适合验证解析和显示链路，但数据展开、序列化和全量加载的成本较高。

本次使用 `data/maps/Beijing_gmapsupp.img` 实测：

| 项目 | 结果 |
| --- | ---: |
| 原始 IMG 文件 | 17.56 MiB |
| 生成的 `map.geojson` | 126.43 MiB |
| 生成的 `pois.json` | 13.38 MiB |
| 生成的 `routing.json` | 43.69 MiB |
| 上述三个数据文件合计 | 约 183.50 MiB |
| 导入进程耗时 | 约 4.89 秒 |
| 导入进程峰值 RSS | 约 532 MiB |
| 单次寻路进程耗时 | 约 2.13 秒 |
| 单次寻路进程峰值 RSS | 约 456 MiB |

测量条件与解释：

- 使用审查时已有的 Mac ARM64 本地构建，`CMAKE_BUILD_TYPE` 为空，未启用 Release 优化。
- 使用 `/usr/bin/time -l` 测量各个独立进程。
- 寻路起点为 `39.9042, 116.4074`，终点为 `39.93, 116.42`，模式为驾车、最短距离。
- 峰值 RSS 不包含主程序和 MapLibre 的渲染开销；两个进程的峰值不能直接相加作为整机峰值。
- 这是单次观察，不是冷启动、多次统计或目标板基准测试。耗时可能受到构建优化、文件缓存及系统负载影响。

此外，当前实现保留已创建的临时地图目录直到退出。反复加载地图会累积临时磁盘数据，尚未形成有容量上限的缓存管理。

证据：

- [最高精度全量读取](../tools/garmin/import_main.cpp)
- [JSON 数据输出](../tools/garmin/import_main.cpp)
- [临时地图目录保留](../core/mapdocument.cpp)

建议：采用按区域、按层级读取的数据访问方式，并建立有容量上限的缓存。可根据设备预算选择 PC 端预转换，或运行时通过格式插件按需读取原始地图，避免每次加载都全量展开为 GeoJSON。

### 3. [P1] 每次规划路线都会重新读取路网、重新建图

每次规划和偏航重算都会启动新的寻路进程，完整解析 `routing.json`，重新构造道路图和转向限制匹配结构。地图不变时，这些工作仍会重复。

进程隔离有利于控制旧解析库的故障影响，但不要求每次查询都重新建立全部数据结构。

证据：

- [每次启动寻路程序](../core/mapdocument.cpp)
- [完整读取路网 JSON](../tools/garmin/route_main.cpp)
- [运行时构图](../core/routing/router.cpp)

建议：将路网预处理为可复用的二进制索引，由寻路服务复用已加载的数据；根据设备条件采用分区加载或文件映射。进程隔离可以保留。

### 4. [P2] 搜索尚未形成索引查询

MBTiles 每次搜索都会扫描最高缩放层级的瓦片并解压名称；佳明名称搜索与附近 POI 查询会遍历地点数组。后台进程避免了 MBTiles 扫描直接阻塞界面，但没有消除扫描开销。

MBTiles 搜索还存在结果完整性问题：先截取前 50 个匹配项，再对结果排序，可能漏掉后续瓦片中的精确匹配。

证据：

- [最高层级瓦片扫描与数量截断](../plugins/mbtiles/place_search.cpp)
- [佳明名称遍历](../core/mapdocument.cpp)
- [附近 POI 遍历](../core/mapdocument.cpp)

建议：建立持久化的名称索引和空间索引，通过统一搜索能力接口提供查询结果、排序、分页与取消操作。

### 5. [P1] 构建与部署尚未形成嵌入式工程闭环

根目录 `CMakeLists.txt` 为空，目前主要从 `mapviewer/` 单独构建，尚无统一的引擎、插件、工具和应用构建入口。

安装配置也存在具体缺口：安装规则只安装主程序。macOS 辅助程序会复制进 app 包，但 Linux 安装没有对应的辅助程序安装规则，部署后可能找不到导入、寻路和搜索程序。

默认地图路径在构建时关联源码目录，也需要在独立部署时改为可配置的数据目录。

Mac ARM64 能运行，只能证明当前桌面环境的一部分兼容性，不能证明低资源 ARM 设备适用。当前审查范围内未见目标板的交叉编译、依赖部署和性能验收闭环。

证据：

- [根构建文件](../CMakeLists.txt)
- [辅助程序复制规则](../mapviewer/CMakeLists.txt)
- [安装规则](../mapviewer/CMakeLists.txt)
- [默认地图路径](../mapviewer/main.cpp)

建议：建立统一 CMake 入口、功能开关、ARM 工具链配置、数据路径配置和安装验证；明确目标设备的内存、GPU、存储及系统环境。

### 6. [P2] 转换工具链尚未覆盖 README 中的承诺

`tools/tilemaker` 已加入仓库，但现有脚本仍依赖外部命令、固定输入路径和当前工作目录，尚未形成可复现的工具链。

当前没有找到完整接入的 OSM PBF → Garmin IMG 转换流程。README 中“支持 OSM PBF”也需要区分“作为离线转换输入”和“运行时直接打开”。目前主程序的加载入口不直接支持 OSM PBF。

证据：

- [现有 OSM PBF → MBTiles 脚本](../scripts/osm_2_mbtile.sh)
- [子模块配置](../.gitmodules)
- [地图加载入口](../core/mapdocument.cpp)

建议：将转换工作明确放在 PC 端工具层，补齐输入输出参数、配置文件、依赖版本、错误处理和结果校验，并分别列出已完成与计划支持的转换路径。

### 7. [P2] 导航仍是开发版能力

已实现单行、车辆准入、静态转向禁令、路线提示、模拟导航和偏航重算。但“完整路线规划导航”仍未全部达到：

- 时段限制目前是遇到未知编码拒绝规划，没有实现按星期和时间判断通行。
- 预计时间按道路类别估算，没有使用实际限速。
- 起终点匹配到最近道路顶点，而非道路上的精确投影点。
- 导航位置匹配、定位误差处理和偏航判定仍需更多真实场景验证。

拒绝忽略未知规则是正确的保护措施，但不能视为已经支持该类规则。

证据：

- [未知条件编码处理](../plugins/garmin/network.cpp)
- [速度估算](../core/routing/router.cpp)
- [最近顶点匹配](../core/routing/router.cpp)
- [导航位置匹配与偏航判定](../mapviewer/map/NavigationController.qml)

建议：将路由和导航服务从具体格式中分离，明确能力边界；增加道路投影匹配、真实轨迹回放、多模式限制和条件规则测试。

### 8. [P2] 仓库职责与验证体系需要进一步收敛

`navit/`、`navitdrv/`、`web/` 中保留了历史源码或实验页面，未纳入当前主程序构建。部分 Web 页面依赖远端脚本、字形或本地 Martin 服务，不应直接计入离线主程序的已完成能力。

当前已有真实地图、整数读取、路网限制、交互和搜索测试，这是有价值的基础。但还缺少目标设备的资源预算、性能回归门槛、部署验证和持续集成。部分真实地图测试依赖本地数据文件，测试数据如何提供也需要工程化。

建议：区分主产品、第三方依赖、实验程序和历史参考代码；保留有价值的内容并标明用途。建立可复现的小型测试数据、目标平台矩阵与性能基线。

## 建议的职责划分

```text
core/          地图生命周期、查询、缓存、统一数据类型
plugins/       Garmin、MBTiles 等格式适配与能力声明
mapviewer/     Qt 界面与渲染适配
lib/           第三方解析库
tools/         PC 端地图转换、索引构建、数据检查
tests/         正确性、性能、部署与目标板测试
```

格式插件按实际数据声明能力，例如：

- 瓦片读取。
- 按区域、按层级查询几何。
- 名称与附近地点搜索。
- 路网与通行规则读取。

不要求每种格式都支持全部能力。例如，栅格 MBTiles 可以提供显示能力，但通常没有名称搜索和路由数据。UI 应通过能力声明决定展示哪些功能。

MapLibre 可继续作为渲染后端，通过适配层接入核心数据接口。应先在目标设备上测量其资源占用，再决定是否需要其他渲染后端。

## 建议实施顺序

1. **明确验收目标**：确定 ARM 目标设备、系统、RAM、GPU、存储，以及地图规模、启动时间、查询延迟和交互帧率预算。
2. **提取核心接口**：分离应用、数据格式、搜索、路由与渲染职责，建立能力声明和插件注册。
3. **调整数据路径**：消除运行时全量 JSON，建立可复用的二进制路网、名称与空间索引，限制缓存容量。
4. **补齐工程闭环**：统一构建入口、交叉编译、依赖安装、辅助程序部署和数据目录配置。
5. **完善转换工具**：形成可复现的 OSM PBF → MBTiles 流程，再补齐 Garmin IMG 转换链路。
6. **完善导航与验证**：增加真实轨迹、条件限制、定位异常及大地图测试，并建立 Release 和目标板性能回归。
7. **整理仓库与文档**：区分已支持、实验性和计划能力，明确历史代码用途。

下一阶段的核心目标应是从“功能可用”推进到“资源开销可控、模块接口稳定、部署可复现”，以此兑现 README 中的设计目标。
