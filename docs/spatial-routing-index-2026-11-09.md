# 几何分块读取与紧凑路网索引

日期：2026-11-09。承接已提交的目录/架构调整 `01f5e9c`。本阶段把 Garmin 显示改为按瓦片查询几何，把规划改为直接读取预编译路网；目标 ARM 板尚未确定。

## 运行链路

```text
IMG（只读）
  └─ 首次预处理
       ├─ geometry.sqlite：空间范围、显示层级、简化后的几何
       ├─ places.sqlite：名称、类别、地址/电话与附近查询
       └─ 临时 routing.cbor → car / bicycle / walk.vgr
                               └─ routing-index.json

MapLibre 请求 z/x/y → 本机瓦片进程 → SQLite 范围查询 → 裁剪 → MVT
路线请求 → 路由进程 → 映射所选模式的 .vgr → 空间匹配与路径搜索
```

导入缓存版本为 `garmin-spatial-graph-v1`，仍按源文件内容寻址，继承 512 MiB 磁盘预算和会话租约。新版本不会把旧 GeoJSON 缓存误当作可用索引。成功完成后才切换地图。显示会话分别持有临时样式和瓦片进程，避免重复加载同一地图时改写旧渲染器正在使用的服务地址。

应用自动完成导入、三种模式编译和缓存发布，并移除中间 `routing.cbor`。缓存命中仅启动瓦片进程；路线首次请求才启动路由进程。运行缓存没有 `map.geojson`、`pois.json` 或文本路网。诊断导入默认仍导出这些文件，便于独立检查解析结果。

## 几何查询与显示

实现位于 `core/geometry/`，工具为 `mapviewer_geometry_service`。

- SQLite R-tree 按瓦片范围筛选对象，结合 `minzoom` 与层级表，逐行读取命中几何。查询不对含几何的结果集做全量排序。
- 几何使用归一化 Mercator 坐标和 CBOR，预生成 8、11、14 三档简化结果；对应显示级别选择一档。点在 14 级出现；道路按类别、面按面积设置最小级别。小面与低级别细节有意省略。
- Boost.Geometry 完成简化、裁剪以及多边形孔洞/分裂处理。简化后无效的面回退到原几何；这不是共享边界的拓扑简化，少量面边界仍可能有细小缝隙。
- 生成标准 MVT，图层名 `garmin`、extent 4096、边缘 buffer 64。线和面截取至瓦片边缘；处理跨日期变更线的候选范围。高于 14 级由 MapLibre 放大最高层级瓦片。
- 渲染仅保留名称、样式类别和 POI 类别；完整地点详情继续查询 `places.sqlite`，路由属性在路网索引中保留。低级别瓦片省略暂不显示的名称和类别字段。
- 服务只监听 `127.0.0.1` 随机端口，并使用每会话随机路径。只接受瓦片路径，不暴露文件目录。独立进程中的同步裁剪不阻塞界面线程，但大瓦片会影响该服务其他请求的延迟。
- SQLite 页缓存 4 MiB，已生成瓦片缓存 16 MiB，最多 8 个连接；单几何输入上限 16 MiB，瓦片图层上限 8 MiB。这些限制不等于整个进程峰值内存上限，裁剪临时对象、套接字及 MapLibre 缓存另占内存。

## 紧凑路网

实现位于 `core/routing/graphstorage.*`，编译/服务入口为 `mapviewer_garmin_route`。

每种模式独立保存节点、边、名称/道路 ID 字符串池、禁转自动机、禁止穿行道路的反向邻接以及节点空间网格。节点和边使用定长记录，路由查询直接从 `QFile::map` 映射读取，不恢复完整 Qt 对象图。路径搜索的队列和状态仍动态分配。

文件以 `VRGRPH01` 开头；120 字节文件头包含十段长度及 SHA-256，所有数字用小端存储。加载时验证校验和、段长、坐标、成本、引用范围、自动机失败链和网格完整性。损坏、截断、版本/模式不匹配的图显式报错。校验会遍历文件，因而首次加载并非完全惰性读盘；系统可回收只读映射页。

节点空间网格为 0.01 度，筛选距离端点 1 公里内的候选，再用球面距离比较。跨日期变更线、极区与距离相同时的选择规则与原全扫描实现对照验证。匹配仍落在最近图节点，尚未实现道路段投影。

同一模式复用映射；切换模式先释放旧图，空闲 60 秒退出。响应中的 `graphBuilds=0`、`graphLoads=1` 可用于确认运行时未重新建图。编译阶段继续使用原有访问限制和转向规则构图，未知条件仍拒绝规划；本次改造没有新增时段规则解码能力。

## 复现命令

从仓库根目录构建，Garmin 增加 Boost 头文件和 Qt Network 依赖，详见 [平台说明](platforms.md)。应用正常选择 IMG 即可自动使用新链路。手工处理需要一个新的输出目录：

```sh
build/tools/mapviewer_garmin_import data/maps/Beijing_gmapsupp.img /tmp/beijing-index --compact
build/tools/mapviewer_garmin_route --compile /tmp/beijing-index/routing.cbor /tmp/beijing-index
build/tools/mapviewer_garmin_route /tmp/beijing-index/routing-index.json \
  39.9042 116.4074 39.93 116.42 car shortest
build/tools/mapviewer_geometry_service /tmp/beijing-index/geometry.sqlite \
  14 13489 6208 /tmp/beijing-tile.pbf
```

手工命令保留 CBOR 以便检查；应用管理的缓存会自动清理该中间文件。省略几何服务的 `z x y output` 参数可启动本机服务，标准输出第一行 JSON 包含其 URL。

## Mac Release 观察

环境：Mac ARM64、Qt 6.10.1，`Beijing_gmapsupp.img`，以下为单次观察，无清空系统文件缓存、无统计分位数，也不是 ARM 目标板承诺。RSS 指辅助进程峰值，不包含主程序/渲染器。

| 项目 | 结果 |
| --- | ---: |
| 几何索引 | 84.56 MiB，284,231 个对象 |
| 地点索引 | 约 27.89 MiB |
| 驾车 / 骑行 / 步行图 | 32.19 / 32.50 / 50.17 MiB |
| 上述五个索引总量 | 约 227.31 MiB，另有少量元数据和字形 |
| 首次 `--compact` 导入（另一次观察） | 7.114 秒，峰值 RSS 477.66 MiB |
| 三种路网模式预编译 | 2.541 秒，峰值 RSS 872.59 MiB |
| 同一 Release 程序读取 CBOR 并建图规划 | 0.904 秒，峰值 RSS 665.53 MiB |
| 直接加载驾车索引并规划相同路线 | 0.209 秒，峰值 RSS 48.72 MiB |
| 两条路径结果 | 均为 4,339.355 米；索引路径建图次数为 0 |
| 持久服务内同模式重复规划（另一次观察） | 约 2.1 毫秒 |
| `14/13489/6208` 单瓦片进程 | 约 46 毫秒，峰值 RSS 18.81 MiB |
| 该瓦片实际读取 | 2,352 个候选，80,918 字节 MVT |

预编译三种模式增加了磁盘占用，以换取运行时更小的内存需求和更快的首次规划。不能把单瓦片数据推导成完整视口或整机内存，也不能把文件映射理解为固定内存保证。

两项预处理是顺序执行的独立进程，其峰值不能直接相加；主程序仍可能同时保留旧地图。地点索引因插入顺序的页布局略有变化，本机重复导入约为 27.89–27.93 MiB。
